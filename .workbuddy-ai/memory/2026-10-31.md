# 2026-10-31

## Database Simplification V2 — implemented and verified (39 tables)

Completed the six agreed consolidations against the real dev database `medora_v1`
(PostgreSQL 18.6, localhost). No destructive migration was needed: none of the six
source tables had ever been deployed, so the simplified shape was written directly
into new migrations instead of create-then-drop.

**Migrations created and applied (all recorded in `schema_migrations`):**
- `004_operations_audit.sql` — `audit_logs` (absorbs appointment status history +
  security events), `notifications`; views `v_appointment_status_timeline`,
  `v_security_events`.
- `005_scheduling_core.sql` — clinic_locations, doctor_availability, doctor_time_off,
  appointments, care_relationships.
- `006_consultations_transcripts.sql` — consultations, consents, recordings,
  transcripts, agent_executions, transcript_versions (+ immutability / reviewer /
  status-sync triggers).
- `007_agent_reports.sql` — medical_reports (publication columns), report_versions
  (review columns), record_update_proposals; approval-assertion functions and
  publication gate.
- `008_followups_proposals.sql`, `009_medical_records.sql` (provenance gate),
  `010_reference_knowledge.sql` (extraction link both ways).

**Key decisions to remember:**
- `report_deliveries` merged into `medical_reports` is only valid because the MVP is
  portal-publication-only. Multi-channel delivery would need a NEW table, not a
  resurrection of the old one.
- Extraction quality/reviewer data lives on `reference_document_versions`, never
  duplicated onto `agent_executions`.
- `audit_logs.action` was replaced by `event_type` (namespaced, e.g.
  `appointment.status_changed`); the security category is bound to the `security.`
  namespace by CHECK.
- Immutability and doctor-authorisation are enforced by DB triggers, not only services.

**Tooling added:**
- `Backend/tests/schema-v2.test.js` (`npm run test:schema`) — 98 assertions, all
  inside one rolled-back transaction.
- `Backend/scripts/validate-dbml.js` (`npm run db:validate`) — 748 checks; proves
  `database/medora.dbml` matches PostgreSQL table-for-table and column-for-column.
- `database/PREFLIGHT_REPORT_V2.md`, `database/DATABASE_ARCHITECTURE_V2.md` (Egyptian Arabic).
- `SCHEMA_ARCHITECTURE.md` and `SCHEMA_DATA_DICTIONARY.md` now carry a SUPERSEDED banner.

**Environment facts worth remembering:**

  at `medora_v1`; `medora_db` does not exist on this server.

## Later same day — unified V2 with the teammate's Admin backend (42 tables)

Merged `da8b0ac` (teammate's Admin backend, = `origin/main`) into local V2 and
reconciled the migration fork. **Key finding: the teammate's work had never
actually been pulled** — `main` was at the parent commit, reflog confirms no pull.
So there was nothing to "preserve" locally; there was a commit to merge.

**Resolution of the fork (important precedent):** the *published* lineage keeps
its numbers, the *unpublished* one moves. `004_admin_workforce` /
`005_admin_account_lifecycle` are byte-identical to the commit (verified by blob
hash). V2 migrations renumbered 004-010 → 006-012, plus new `013`.

- `006_audit_logs_unification.sql` **transforms** the teammate's `audit_logs`
  in place (`action` → `event_type` + `event_category`, backfilled then dropped),
  copies `security_events` into it, then drops `security_events`. It does NOT
  create `audit_logs`/`notifications` — 005 owns them.
- `007_scheduling_core.sql` no longer creates `clinic_locations` — 004 owns it.
- `013_audit_identity_reference.sql` fixes a real bug: the append-only trigger
  blocked `ON DELETE SET NULL` on `actor_user_id`, so **no user with audit
  history could ever be deleted**. Content stays immutable; identity pointers may
  be nulled but never reassigned.
