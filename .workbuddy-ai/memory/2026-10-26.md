### Phase 2 / 003 decision document
Wrote `PHASE2_003_DECISIONS.md` — full analysis of DB.md §7's four open decisions, with
recommendations and the resulting DDL sketch. No migration written or executed.

Recommendations issued:
1. DOB/phone/gender: nullable in DB, completeness enforced at API (`profile_completed_at`).
2. Profile lifecycle: auto-create in the registration transaction + idempotent backfill
   (costs one INSERT in `authService.registerPatient` — flagged as needing explicit approval
   because DB.md §9 says Phase 2 must not rewrite auth).
3. Specialty: normalised `specialties` table (NOT `departments`), FK NOT NULL + RESTRICT.
4. `license_number`: admin-only write, doctor read-only, NOT NULL + unique, plus optional
   `license_verified_at` / `license_verified_by`.

Key repo evidence gathered: the frontend has TWO conflicting department vocabularies —
`src/lib/mock/departments.ts` has 12 (incl. gynecology, ent, ophthalmology, psychiatry,
radiology, oncology), `src/lib/mock/doctors.ts` has 6 — and the 6 are a strict subset of
the 12. Seeding `specialties` with the 12 aligns with both.

Note for 003: the runner wraps each file in its own transaction, so migration files must NOT
contain BEGIN/COMMIT. Also `CURRENT_DATE` is not immutable and must not appear in a CHECK.
