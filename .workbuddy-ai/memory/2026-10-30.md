## Revision 2 — after reading all 45 DBML tables

Owner pushed back that the plan was written without reading the full schema. Correct. Re-read
`database/medora.dbml` end to end (45 tables, 129 relationships, 8 table groups),
`SCHEMA_ARCHITECTURE.md`, `SCHEMA_DATA_DICTIONARY.md`, `medora.dbdiagram`.

Errors found in revision 1 and fixed:

1. **Migration number collision (blocking).** `SCHEMA_ARCHITECTURE.md` §11 already assigns
   `004` to scheduling and `005` to consultation capture. `Backend/scripts/lib/migrations.js:79`
   throws on duplicate version prefixes, so the proposed `004_admin_workforce` would break
   `db:migrate`. Resolution: renumber — admin takes 004/005, existing stages shift to 006–014,
   old stage 012 (notifications/audit/security) is absorbed into 005.
2. `audit_logs`, `security_events`, `notifications` already fully designed at `medora.dbml:953–1027`.
   Reuse them; do not invent a trimmed audit table.
3. `audit_logs.actor_user_id` **does** have a relationship (`:1194`, ON DELETE SET NULL).
4. `doctor_availability` / `doctor_time_off` / `appointments` are the designed source for
   availability, duty and next shift → dropped the proposed `duty_status` column (would be a
   second source of truth). `duty` returns "off", `onDuty` is 0 until scheduling lands.
5. `specialties` is designated as the Departments table (`:112`, Admin.md §6.4) → department
   model is now an explicit decision, not an assumption.
6. No photo/avatar column exists anywhere and storage is open decision #6 → dropped `photo_url`.
7. Invitation table renamed `account_invitations` → `user_invitations` (open decision #14).
8. Docs that must move with the migrations: DBML (incl. TableGroup entries and status legend),
   SCHEMA_ARCHITECTURE §10/§11/§12, SCHEMA_DATA_DICTIONARY §2/§10 — not just the DBML.
9. Rollback must not sit in `database/migrations/` (the runner would auto-apply it);
   use `database/rollback/`.

Confirmed genuine design gaps across all 45 tables: no staff/employment profile, no doctor
DOB/years/location, no non-clinical organizational unit, no invitation table, no avatar.

## Bug: doctor sign-in bounced to /login

`test1@medora.local` was valid (active, Argon2id hash, role doctor, both invitations consumed).
`LoginPage` sent every non-admin to `/patient/dashboard`; the patient `RouteGuard` rejected the
doctor role and redirected to `/login`, so login looked broken. Repeated attempts could also trip
the 10-per-15-minute login limiter.

Fix: `src/lib/role-home.ts` (admin→admin, patient→patient, doctor/receptionist→`/workspace`,
unknown→null), used by `LoginPage` and `RouteGuard`; new guarded `/workspace` page for doctor and
staff; unknown roles get an explicit message instead of a redirect loop.

Recovery path for a lost password: doctor detail → Quick Actions → Reset Password (wired in
step 8) issues a one-time link.

### Verification of the login fix

`npm run dev` start cleanly; `npm run build` must be re-run before `next start`.

## Bug: login 500 "An unexpected error occurred"

Cause: Next fell back to `:3001` (3000 busy), so the browser Origin was `http://localhost:3001`;
the backend allowlist had only `:3000` and the CORS callback threw a plain Error → 500.
The password was valid all along (`test1@medora.local` / `Test1234`).

Fix in `Backend/server.js`: any loopback origin on any port is allowed when
`NODE_ENV !== "production"`; denied origins return `403 cors_origin_denied` and log
`[CORS] Blocked origin`. Production keeps the explicit allowlist.

Also: two `next dev` instances shared `.next`, producing hashed-chunk 404s. Consolidated to one
stack on 3000/5000. `rm -rf .next` is blocked above 50 files by the shim; `mv .next <temp>` works.
Verified `test1` login through Edge → `/workspace`.
